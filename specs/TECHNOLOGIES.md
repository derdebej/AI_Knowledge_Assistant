# Technologies — AI Knowledge Assistant

| Technology | Purpose | Why chosen | Alternatives considered |
|---|---|---|---|
| **Python 3.12** | Backend language | Dominant language for AI/RAG tooling (OpenAI SDK, LangChain, pgvector clients all first-class); type hints + async support mature enough for a typed, production-style API | Node.js/TypeScript (would unify FE/BE language, but weaker AI ecosystem); Go (excellent for the API layer, poor RAG/embedding ecosystem) |
| **FastAPI** | Web framework | Native async, Pydantic-based validation gives request/response schemas "for free," automatic OpenAPI docs, first-class SSE/streaming support needed for §2.7 of [RAG_PIPELINE.md](RAG_PIPELINE.md) | Flask (no native async, weaker validation story); Django (batteries-included ORM/admin are unneeded weight for an API-only backend) |
| **Pydantic (v2)** | Data validation & settings | Powers FastAPI's request/response schemas and `Settings` (env-driven config); v2's Rust core gives real performance headroom over v1 | Marshmallow, attrs+cattrs (both viable, less integrated with FastAPI) |
| **SQLAlchemy 2.0 (async)** | ORM / query builder | Mature, explicit, works cleanly with pgvector via a community type extension; async engine matches FastAPI's async request handling; keeps SQL construction parameterized (SQL-injection prevention, [SECURITY.md](SECURITY.md) §6) | Raw `asyncpg` (faster but pushes schema/migration discipline entirely onto hand-written SQL); Tortoise ORM (smaller ecosystem) |
| **Alembic** | Schema migrations | Standard companion to SQLAlchemy; versioned, auditable schema history including the `vector` extension and HNSW index creation ([DATABASE.md](DATABASE.md) §8) | Manual SQL migration scripts (no dependency tracking, easy to apply out of order) |
| **PostgreSQL 16** | Primary datastore | One transactionally-consistent store for relational data *and* vectors (via pgvector) avoids a two-database architecture and dual-write consistency problems; free, self-hostable, works identically in Docker Compose and any future cloud deployment | MySQL (no first-class vector extension); SQLite (no pgvector, wrong tool for concurrent multi-user access) |
| **pgvector** | Vector similarity search | Adds vector column types + ANN indexing (HNSW/IVFFlat) directly to Postgres — see full HNSW rationale in [DATABASE.md](DATABASE.md) §5; avoids running/paying for/operating a separate vector database for a project at this data scale | Pinecone (managed, but external dependency + cost for a local-first portfolio project); Qdrant/Weaviate (excellent, but split relational+vector storage adds architectural complexity not justified until scale demands it — the `VectorStore` port keeps this migration cheap later, see [ARCHITECTURE.md](ARCHITECTURE.md) §6) |
| **LangChain** | Text splitting, PDF loading utilities | Used narrowly, behind the `Chunker`/`DocumentParser` ports, for well-tested utilities (`RecursiveCharacterTextSplitter`) where reimplementing would be pure boilerplate with no learning or architectural value; explicitly *not* used to structure the application itself (no LangChain "chains" wrapping the core RAG logic) — see [ARCHITECTURE.md](ARCHITECTURE.md) §2.5 and [PROJECT_OVERVIEW.md](PROJECT_OVERVIEW.md) | Hand-rolled regex/NLTK-based splitter (more code, no real benefit over a well-tested library for this well-solved problem) |
| **LangGraph** | *Not used in MVP* | The ingestion and query pipelines are linear DAGs with no cycles, branching agent behavior, or multi-step tool use — a directly-composed sequence of service calls is simpler to read, debug, and unit-test than a graph abstraction for a linear flow (see [ARCHITECTURE.md](ARCHITECTURE.md) §9). Reconsidered if post-MVP work adds multi-hop retrieval (retrieve → judge sufficiency → re-query) or agentic tool use, where LangGraph's cyclic-graph model genuinely earns its complexity | Plain async function composition (chosen); a hand-rolled state machine (unnecessary — no state machine complexity exists yet) |
| **OpenAI API** | Embeddings + LLM generation | Best-documented, most reliable API for a portfolio project graders will recognize; `text-embedding-3-small` and `gpt-4o-mini` give strong quality-per-dollar for MVP scale (see [RAG_PIPELINE.md](RAG_PIPELINE.md) §1.6, §2.7); both are behind `EmbeddingProvider`/`LLMProvider` ports so the choice is not architecturally load-bearing | Anthropic Claude (equally viable behind the same port — good candidate for demonstrating the swap in practice); local models via Ollama (removes API cost/dependency but adds infra complexity and lowers baseline quality — good post-MVP addition, see [ROADMAP.md](ROADMAP.md)) |
| **React 18** | Frontend framework | Ubiquitous, strong ecosystem for the streaming-chat + file-upload UI patterns this project needs; pairs naturally with TypeScript | Vue, Svelte (both fine choices; React chosen for broadest reviewer familiarity) |
| **TypeScript** | Frontend language | Type-safe contract with backend Pydantic schemas (mirrored types in `frontend/src/types/`) catches integration bugs at compile time rather than in the browser | Plain JavaScript (no compile-time contract checking) |
| **TailwindCSS** | Styling | Fast to build a clean, consistent UI without hand-rolling a design system for a project where the UI is a means to demonstrate the backend, not the primary deliverable | CSS Modules, styled-components (both more setup for less payoff here) |
| **Vite** | Frontend build tool | Fast dev server + build, minimal config, standard pairing with React+TS in 2025+ | Create React App (unmaintained), Next.js (SSR/routing features unneeded for a single-page authenticated app) |
| **Docker / Docker Compose** | Local dev environment & deployment packaging | One-command local environment (`docker compose up`) is a baseline expectation for a "production-oriented" project and removes "works on my machine" ambiguity for reviewers | Bare-metal setup instructions only (worse reviewer experience); Nix (steeper learning curve, less universally recognized) |
| **GitHub Actions** | CI/CD | Free for public repos, zero infrastructure to maintain, directly visible to reviewers browsing the repo (badge + Actions tab) | GitLab CI, CircleCI, Jenkins (all viable; GitHub Actions chosen for GitHub-hosted-repo convenience) |
| **pytest / pytest-asyncio** | Backend testing | Standard, async-native, fixture system fits the layered architecture's fake-adapter testing approach (see [TESTING.md](TESTING.md) §5) | `unittest` (more boilerplate, weaker fixture ergonomics) |
| **ruff** | Lint + format (backend) | Single fast tool replacing flake8+isort+black; low CI overhead | flake8 + black + isort (functionally similar, more moving parts) |
| **mypy** | Static type checking (backend) | Catches type errors across the layered architecture's interfaces (ports/adapters) before runtime | pyright (also good; mypy chosen for broader Python ecosystem convention) |
| **structlog** | Structured logging | JSON-structured logs with request-ID binding, needed for the observability requirements in [SECURITY.md](SECURITY.md) §8 and NFR-6 | Standard `logging` with manual JSON formatting (more code for the same result) |
| **RAGAS** | RAG evaluation framework | Purpose-built metrics (faithfulness, answer relevancy, context relevancy) matching exactly what [EVALUATION.md](EVALUATION.md) needs to measure, avoiding hand-rolled LLM-judge prompting | Hand-rolled LLM-judge scripts (more maintenance, reinvents a well-covered wheel) |

## Summary of the "replaceable by design" set

Per the project's core architectural requirement, four technology choices are explicitly wrapped behind interfaces rather than baked into business logic — see [ARCHITECTURE.md](ARCHITECTURE.md) §6 for the full table: embedding provider, LLM provider, vector store, document parser. Everything else in this table (FastAPI, SQLAlchemy, Postgres-as-relational-store, React) is treated as a foundational choice, not something the architecture needs to abstract away — abstracting *everything* would be the overengineering the project brief explicitly warns against.
